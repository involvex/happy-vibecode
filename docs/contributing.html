Contributing

Thank you for your interest in contributing to Happy Vibecode! This guide covers the development workflow, coding standards, and best practices.

Getting Started

  1. Fork the repository on GitHub
  2. Clone your fork locally:
    Terminal 
    git clone https://github.com/your-username/happy-vibecode.git
cd happy-vibecode
bun install
  3. Create a feature branch from main:
    Terminal 
    git checkout -b feature/your-feature-name

Code Standards

TypeScript

  • Strict mode is enabled across all packages
  • Always use proper types — no any or untyped code
  • Use Zod schemas from packages/shared for runtime validation
  • Prefer interface over type for object shapes

Formatting

Terminal 
# Format all code
bun run format

# Lint and auto-fix
bun run lint:fix
  • Uses Prettier with @involvex/prettier-config
  • Linter: oxlint (configured per package)
  • Run bun run format before committing

Path Aliases

Use @happy-vibecode/* for cross-package imports:

TypeScript 
import {createDb} from '@happy-vibecode/db'
import type {LLMProvider} from '@happy-vibecode/shared'
import {api} from '@happy-vibecode/api'

Architecture Patterns

Adding an API Endpoint

  1. Create a route file in packages/api/src/routes/
  2. Define the Hono router with typed bindings
  3. Mount it in packages/api/src/index.ts
  4. Add Zod schemas in packages/shared/src/schema/
Example Route 
import {authMiddleware, type ApiEnv} from '../middleware/auth.js'
import {Hono} from 'hono'

export const myRouter = new Hono<{
	Bindings: ApiEnv
	Variables: {userId: string}
}>()

myRouter.use('*', authMiddleware)

myRouter.get('/', async c => {
	const userId = c.get('userId')
	// ... implementation
	return c.json({data: []})
})

Adding a Database Table

  1. Define the table in packages/db/src/schema.ts
  2. Generate migration: bun run -F @happy-vibecode/db generate
  3. Review the migration in packages/db/drizzle/
  4. Apply migration: bun run -F @happy-vibecode/db migrate
  5. Update wrangler.jsonc if adding new bindings

Adding a Frontend Route

  1. Create a page file in apps/web/app/ (uses TanStack Router via vinext)
  2. Use existing components from apps/web/app/components/
  3. Fetch data via API hooks or vinext loaders

Commit Conventions

We use Conventional Commits:

Commit Format 
type(scope): description

# Examples:
feat(auth): add GitHub OAuth callback handling
fix(chat): resolve WebSocket reconnection loop
docs(readme): update installation instructions
refactor(api): extract rate limiting middleware
test(db): add user CRUD tests
Type Description
feat New feature
fix Bug fix
docs Documentation changes
refactor Code refactoring (no behavior change)
test Adding or updating tests
chore Build, CI, or tooling changes
perf Performance improvements

Testing

Terminal 
# Run all tests
bun run test

# Run tests for a specific package
bun run -F @happy-vibecode/api test

# Run type checking
bun run typecheck
Before Submitting a PR
Always run these checks before opening a pull request:
bun run format
bun run lint:fix
bun run typecheck
bun run test

Pull Request Process

  1. Ensure your branch is up to date with main
  2. Run all checks (format, lint, typecheck, test)
  3. Write a clear PR description referencing any related issues
  4. Keep changes focused — one feature or fix per PR
  5. Update documentation if adding new features
  6. Wait for CI checks to pass

Project Structure Reference

Task Key Files
Add API endpoint packages/api/src/routes/, mount in packages/api/src/index.ts
Add database table packages/db/src/schema.ts, migrations in packages/db/drizzle/
Add shared type packages/shared/src/schema/, export in packages/shared/src/index.ts
Modify worker routing apps/web/worker/index.ts
Add Durable Object apps/web/worker/, register in wrangler.jsonc
Add frontend route apps/web/app/ (vinext + TanStack Router)
Add mobile screen apps/mobile/app/ (Expo Router)
Add styling apps/web/app/globals.css, Tailwind config

Security

  • Never commit secrets, API keys, or tokens to the repository
  • Use wrangler secret put for production secrets
  • Validate all external input with Zod schemas
  • Follow the principle of least privilege for API endpoints
  • See SECURITY.md for vulnerability reporting
